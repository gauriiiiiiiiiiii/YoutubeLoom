1. WHAT THIS PROJECT IS
================================================================================

YouTube Loom does three things in sequence:

   1. RECORDS your screen (+ microphone, + optional webcam picture-in-picture).
   2. PREVIEWS the recording and lets you edit title / description / privacy.
   3. UPLOADS it straight to your YouTube channel.

The philosophy is "No server storage, no file size limits." Everything heavy -
capturing, holding, uploading - happens IN YOUR BROWSER. The app's backend is
just two tiny functions whose only job is to keep the OAuth client_secret
hidden from the browser.

  Mental model: the browser does all the work; the server only whispers a
  password to Google when needed.

features. This app is clever glue that wires them together, then talks to
YouTube.

3. THE END-TO-END JOURNEY
================================================================================

Everything in the project is a detail of one of these five steps:

   +--------+   +----------+   +---------+   +---------+   +--------+
   | 1. LOG |-->| 2.RECORD |-->| 3.STORE |-->| 4. STOP |-->| 5.     |
   | IN     |   | SCREEN + |   | CHUNKS  |   | COMBINE |   | UPLOAD |
   | YOUTUBE|   | MIC/CAM  |   |(IndexDB)|   | CHUNKS  |   | TO YT  |
   +--------+   +----------+   +---------+   +---------+   +--------+

   1. Log in        - Google hands the app a token (a temporary keycard).
   2. Record        - browser captures the chosen screen + mic (+ webcam).
   3. Store chunks  - every 5 s a piece is saved to IndexedDB; memory stays low.
   4. Stop&combine  - the pieces are stitched into one file.
   5. Upload        - the file goes to YouTube in 5 MB slices; you get a link.

Folder -> step:
   lib/         The engine (record, store, upload) - steps 2-5
   components/  The buttons and screens
   app/         The pages + login server functions - step 1
   tests/       Automated checks

4. lib/recorder.ts - SCREEN RECORDING
================================================================================

Defines ScreenRecorder. Its job: turn "user clicked record" into a stream of
video chunks.

THE CORE IDEA
A recording is really FOUR separate streams that must be merged into one -
screen video, screen audio (if allowed), microphone, and (optionally) webcam.

INSIDE start()

1-3. Capture the sources. Screen via getDisplayMedia (shows the "Choose what to
share" dialog), mic and webcam via getUserMedia:

     this.screenStream = await navigator.mediaDevices.getDisplayMedia({
       video: { width: { ideal: 1920 }, height: { ideal: 1080 }, frameRate: { ideal: 30 } },
       audio: { echoCancellation: true, noiseSuppression: true, sampleRate: 44100 },
     });
     this.micStream = await navigator.mediaDevices.getUserMedia({ audio: { ... } });
     if (this.options.enableWebcam) {
       this.webcamStream = await navigator.mediaDevices.getUserMedia({ video: { ... } });
     }

"ideal" means "prefer this, accept what you can get." Each await pauses until the
user grants (or cancels).

4. Assemble the video track. Webcam on -> hand both streams to VideoCompositor
(Part 5), which returns one combined track. Webcam off -> use the raw screen
track.

5. Mix the audio. You can't just add two audio tracks - you must BLEND them.
AudioContext is the mixing bus:

     const audioContext = new AudioContext();
     const destination = audioContext.createMediaStreamDestination();
     // pipe screen audio (if any) + mic into destination; take the one merged track

No system audio? Only the mic flows in - no error.

6. Start recording. Pick a codec, then emit a chunk every 5 seconds:

     this.mediaRecorder = new MediaRecorder(this.combinedStream, {
       mimeType: this.getSupportedMimeType(),  // vp9 -> vp8 -> h264 -> webm (first supported)
       videoBitsPerSecond: 2_500_000,          // 2.5 Mbps
       audioBitsPerSecond: 128_000,            // 128 kbps
     });
     this.mediaRecorder.ondataavailable = (e) => {
       if (e.data.size > 0) this.options.onDataAvailable?.(e.data);
     };
     this.mediaRecorder.start(5000);           // <- the key to "no file size limits"

start(5000) is why unlimited recordings work: instead of holding the whole video
in RAM, it fires ondataavailable every 5 s with a small chunk, which gets saved
to IndexedDB.

7. Catch the browser's own Stop button:

     screenVideoTrack.onended = () => this.stop();

If the user clicks the browser's floating "Stop sharing" bar, the screen track
ends and this stops recording gracefully.

OTHER METHODS
   stop()                    Stops the recorder, calls cleanup(), returns an
                             in-memory fallback blob.
   cleanup()                 Crucial: stops every track, which turns off the
                             camera light and the "sharing" indicator.
   pause() / resume()        Exist but aren't wired to any UI (see Part 14).
   updateWebcamPosition/Size Forward live changes to the compositor.
   isSupported() (static)    Checks the browser has the required APIs.

TAKEAWAY: the 5-second chunk + callback means the whole video never sits in RAM -
a steady drip of blobs goes straight to IndexedDB.

5. lib/compositor.ts - THE WEBCAM OVERLAY
================================================================================

Defines VideoCompositor. Problem it solves: you have two videos (screen +
webcam) but a recording can hold only ONE video track.

THE CORE IDEA - A PAINTER'S CANVAS
Create an invisible <canvas>; many times a second, paint the screen then paint
the webcam in a corner; then turn the canvas into a video stream. The canvas is a
flipbook - the sequence of frames IS the video. Same technique as OBS or Loom.

THE ANIMATION LOOP (the heart of it)

     const frameInterval = 1000 / this.options.frameRate;  // 15fps -> ~66ms/frame
     let lastFrameTime = 0;

     const composite = (timestamp) => {
       if (timestamp - lastFrameTime >= frameInterval) {
         this.ctx.drawImage(screenVideo, 0, 0, this.canvas.width, this.canvas.height); // screen
         this.ctx.save();
         this.roundRect(this.ctx, x, y, w, h, radius);   // carve a rounded window
         this.ctx.clip();
         this.ctx.drawImage(webcamVideo, x, y, w, h);     // webcam inside it
         this.ctx.stroke();                               // subtle white border
         this.ctx.restore();
         lastFrameTime = timestamp;
       }
       this.animationId = requestAnimationFrame(composite);
     };
     this.animationId = requestAnimationFrame(composite);

     this.compositeStream = this.canvas.captureStream(this.options.frameRate); // <- magic line

Three things to understand:
   - requestAnimationFrame runs composite ~60x/sec (smooth).
   - The throttle (if timestamp - lastFrameTime >= frameInterval) means we only
     REDRAW ~15x/sec - full-res draws are expensive, so 15fps keeps CPU sane.
   - clip() + roundRect() give the PiP its rounded corners; save()/restore()
     isolate the clip from the next full-screen draw.

captureStream() converts the ongoing painting into the single video track the
recorder records.

Webcam sizing assumes 16:9:

     const webcamWidth  = (this.canvas.width * this.options.webcamSize) / 100;
     const webcamHeight = (webcamWidth * 9) / 16;  // a 4:3 cam gets stretched (Part 14)

Defaults: bottom-right, 20% of screen width, 12px corners, 15 fps. stop() calls
cancelAnimationFrame and stops the tracks (without it, the loop burns CPU
forever).

TAKEAWAY: a real-time render loop paints screen-then-webcam onto a hidden canvas
at 15fps, and captureStream() turns that into a video track.

6. lib/indexdb.ts - THE CHUNK DATABASE
================================================================================

Defines IndexedDBStorage. The recorder emits a chunk every 5 s; this catches and
holds them.

WHY NOT A NORMAL ARRAY?
A one-hour recording could be gigabytes - an array crashes the tab and a reload
loses everything. IndexedDB is an on-disk browser database: it survives reloads
and handles large blobs. Chunks go to disk immediately, so memory stays
near-empty. THIS is what "no file size limits" means.

MENTAL MODEL - A FILING CABINET
Database = the cabinet, object store = a drawer, records = folders (one chunk
each).

     interface VideoChunk {
       id: number;          // auto-assigned, increasing
       blob: Blob;          // the 5-second video piece
       timestamp: number;   // for ordering
       recordingId: string; // which session it belongs to
     }

THE CALLBACK-TO-PROMISE PATTERN
IndexedDB predates Promises, so nearly every method wraps its onsuccess/onerror
events in a Promise. Once you see it, every method reads the same:

     return new Promise((resolve, reject) => {
       const request = store.add(chunk);
       request.onsuccess = () => resolve(request.result);
       request.onerror   = () => reject(new Error('Failed to store chunk'));
     });

KEY METHODS
   init()               Opens the DB; on first run creates the store + the
                        recordingId/timestamp indexes.
   storeChunk(blob)     Lazy-inits, adds {blob, timestamp, recordingId}, returns
                        the new id.
   getAllChunks()       Grabs this session's chunks (via the recordingId index)
                        and SORTS by timestamp - order matters or the file breaks.
   combineChunks()      The payoff - concatenates all blobs into one Blob.
   clearChunks()        Deletes only this recording's chunks (via a cursor).
   clearAllRecordings() store.clear() - wipes everything (used on startup).
   getTotalSize()       Sums chunk sizes; the UI polls it every 2 s.
   close()              Closes the connection.

     async combineChunks() {
       const chunks = await this.getAllChunks();
       const blobs = chunks.map((c) => c.blob);
       return new Blob(blobs, { type: blobs[0]?.type || 'video/webm' });
     }

TAKEAWAY: the disk buffer between recording and uploading. Chunks stream in, sit
safely on disk tagged by recordingId, then get reassembled in order.

7. lib/youtube-auth.ts - LOGIN & TOKENS (OAuth 2.0)
================================================================================

No class - just functions that prove you're allowed to upload to your channel.

OAUTH IN PLAIN TERMS - A HOTEL KEYCARD
You log in at the front desk (Google), which hands the app an ACCESS TOKEN
(opens the door, expires in ~1 hour) and a REFRESH TOKEN (a renewal slip for a
fresh keycard). The app shows the access token to YouTube on every upload.

TWO NOTABLE CHOICES
   - Scope is youtube.upload ONLY, not full account access. The broad "youtube"
     scope is restricted and needs a formal Google audit; youtube.upload only
     shows an "unverified app" warning. This dodges a huge verification headache.
   - The token is split across THREE localStorage keys.

     interface YouTubeToken {
       accessToken: string;
       refreshToken?: string;  // not always returned
       expiresAt: number;      // ABSOLUTE ms timestamp, not a duration
     }

THE FUNCTION THE UPLOADER ACTUALLY CALLS - a decision tree that always returns
either a working token or a clear null:

     export async function getValidAccessToken() {
       const token = getStoredToken();
       if (!token) return null;                          // never logged in
       if (isTokenExpired(token)) {
         if (!token.refreshToken) { clearStoredToken(); return null; }  // can't renew
         try {
           return (await refreshAccessToken(token.refreshToken)).accessToken;
         } catch {
           clearStoredToken(); return null;              // renewal failed
         }
       }
       return token.accessToken;                          // still valid
     }

THE 5-MINUTE BUFFER - treat a token as expired early so it never dies mid-upload:

     export function isTokenExpired(token) {
       return Date.now() > token.expiresAt - 5 * 60 * 1000;
     }

Supporting functions: startOAuthFlow() (builds the Google URL with
access_type:'offline' + prompt:'consent' and redirects), exchangeCodeForToken()
and refreshAccessToken() (both call our own server, not Google, because they need
the secret), storeToken/getStoredToken/clearStoredToken, and isAuthenticated().

TAKEAWAY: a keycard manager. Narrow scope, secret-only-on-server, and the
5-minute buffer are the choices that matter.

8. lib/youtube-upload.ts - THE UPLOAD ENGINE
================================================================================

Defines YouTubeUploader. Takes the combined Blob and pushes it to YouTube in
pieces, reporting progress.

WHY RESUMABLE + CHUNKS?
One giant request is fragile - a blip means starting over. YouTube's resumable
protocol: (1) announce the video's metadata to get a session URL, (2) send the
file in 5 MB slices, (3) YouTube tracks received bytes so a break can resume.

THE TOP-LEVEL RECIPE

     async upload(videoBlob, metadata) {
       try {
         this.uploadUrl = await this.initiateUpload(videoBlob.size, metadata); // step 1
         await this.uploadChunks(videoBlob);                                    // step 2
         const videoId = this.getVideoId();                                     // step 3
         this.reportProgress({ percentage: 100, status: 'complete', videoId });
         return videoId;
       } catch (error) {
         this.reportProgress({ status: 'error', error: message });
         throw error;
       }
     }

Step 1 - initiateUpload() sends ONLY metadata and reads the session URL from the
Location header (missing -> throws). Title/privacy are locked in here, before any
bytes move.

Step 2 - uploadChunks() loops: slice 5 MB, send, advance, report progress.
blob.slice() is cheap (a range reference, not a copy).

Step 3 - the retry logic is where robustness lives:

     const response = await fetch(this.uploadUrl, {
       method: 'PUT',
       headers: { 'Content-Range': `bytes ${start}-${end}/${total}` },
       body: chunk,
     });

     if (response.status === 200 || response.status === 201) {
       this.uploadedVideoId = (await response.json()).id;  // capture id from final chunk
       return;
     }
     if (response.status === 308) return;                  // "Resume Incomplete" -> next chunk
     if (response.status >= 500 && attempt < retries) {
       await this.delay(1000 * Math.pow(2, attempt));      // backoff 1s -> 2s -> 4s
       continue;
     }

The three responses: 308 = keep going (normal for every chunk but the last),
200/201 = final chunk, body has the video id, 5xx = retry with backoff.

  History note: an earlier version fetched the id with a separate request, which
  caused a YouTube API error. Grabbing id from the final chunk's body fixed it.

resumeUpload() asks "how many bytes did you get?" and re-sends only the tail -
but it's dead code (never called; see Part 14).

Helpers: generateDefaultTitle() -> "Screen Recording - Jul 19, 2026 at 05:48 PM",
and getYouTubeUrl(id) -> "https://www.youtube.com/watch?v={id}".

TAKEAWAY: announce metadata -> get session URL -> stream 5 MB PUTs tagged with
Content-Range. Built to survive a shaky connection (minus the unused auto-resume).

9. app/ - PAGES & SERVER ROUTES
================================================================================

In Next.js's App Router, the folder structure IS the routing:

   app/
   |-- layout.tsx              -> wraps EVERY page (the shell)
   |-- page.tsx                -> "/"                       (see Part 10)
   |-- globals.css             -> global styles
   |-- auth/callback/page.tsx  -> "/auth/callback"          (Google redirects here)
   +-- api/auth/
       |-- exchange/route.ts    -> POST /api/auth/exchange   (server)
       +-- refresh/route.ts     -> POST /api/auth/refresh    (server)

layout.tsx - THE SHELL
Loads the Inter font (as CSS variable --font-inter), sets page metadata
(title/description/favicon), and - importantly - wraps everything in
<ToastProvider>. That one wrap is why any component anywhere can call useToast().

THE TWO SERVER ROUTES - WHY THEY EXIST
Exchanging the login code and refreshing tokens both need client_secret, which
must never reach the browser. These routes are the app's ONLY server logic and
exist purely to hold that secret. exchange is a secure relay:

     export async function POST(request) {
       const { code } = await request.json();
       if (!code) return NextResponse.json({ error: '...' }, { status: 400 });

       const params = new URLSearchParams({
         code,
         client_id: process.env.NEXT_PUBLIC_YOUTUBE_CLIENT_ID,
         client_secret: process.env.YOUTUBE_CLIENT_SECRET,   // <- server-only
         redirect_uri: process.env.NEXT_PUBLIC_YOUTUBE_REDIRECT_URI,
         grant_type: 'authorization_code',
       });
       const response = await fetch(YOUTUBE_TOKEN_ENDPOINT, {
         method: 'POST',
         headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
         body: params.toString(),
       });
       const data = await response.json();
       return NextResponse.json({
         accessToken: data.access_token,
         refreshToken: data.refresh_token,
         expiresIn: data.expires_in,
       });
     }

The NEXT_PUBLIC_ prefix IS the security boundary: prefixed vars ship to the
browser; YOUTUBE_CLIENT_SECRET (no prefix) stays server-side. refresh is nearly
identical but uses grant_type:'refresh_token' and returns no new refresh token.

auth/callback/page.tsx - THE LANDING PAD
Google redirects to /auth/callback?code=XXXX. This page reads the code, calls
exchangeCodeForToken, then redirects to /?auth=success. It's wrapped in <Suspense>
because in Next 15, useSearchParams() build-errors without a Suspense boundary
(same pattern as the home page).

TAKEAWAY: the app/ layer is thin - layout provides font + toasts, two routes
guard the secret, the callback completes the exchange. All real UI weight is in
the home page.

10. app/page.tsx - THE HOME PAGE (THE CONDUCTOR)
================================================================================

Every file so far was an instrument; this is the conductor. It holds all the
state and calls the engine at the right moments.

THE STATE IS THE APP'S MEMORY (~10 useState values): videoBlob, downloadUrl,
isAuthd, uploading, uploadProgress, youtubeUrl, videoTitle, videoDescription,
privacyStatus (default 'unlisted'), uploadError.

  KEY INSIGHT: the UI is a FUNCTION of these values. There's no "current screen"
  variable - the combination of state IS the screen:
     videoBlob === null            -> recorder
     videoBlob set                 -> preview
     uploadProgress set            -> progress bar

THE UPLOAD HANDLER is where the engine gets called - note how the progress
callback wires straight into React state:

     const handleUploadToYouTube = async () => {
       const accessToken = await getValidAccessToken();
       if (!accessToken) throw new Error('Not authenticated. Please connect to YouTube first.');

       const uploader = new YouTubeUploader(accessToken, (progress) => setUploadProgress(progress));
       const videoId = await uploader.upload(videoBlob, {
         title: videoTitle, description: videoDescription, privacyStatus,
         tags: ['screen recording', 'youtube loom'],
       });
       setYoutubeUrl(getYouTubeUrl(videoId));
       toast('Video uploaded successfully!', 'success');
     };

THE MOUNT EFFECT restores login on refresh and detects the callback's
?auth=success flag, then scrubs it from the URL so a refresh doesn't re-toast:

     useEffect(() => {
       setIsAuthd(isAuthenticated());
       if (searchParams.get('auth') === 'success') {
         setIsAuthd(true);
         window.history.replaceState({}, '', '/');
         toast('Connected to YouTube', 'success');
       }
     }, [searchParams, toast]);

Other handlers: handleRecordingComplete(blob) sets downloadUrl =
URL.createObjectURL(blob) for the preview; handleNewRecording() revokes that URL
(frees memory) and resets state.

THE RENDER is just conditional sections - {condition && <section>} - for header,
auth card, <RecordingControls>, <UploadProgress>, and the preview/edit form. That
chain of booleans IS the state machine.

11. components/ - THE UI PIECES
================================================================================

Four components. RecordingControls is the only "smart" one; the rest are
presentational.

RecordingControls.tsx - THE CONTROL PANEL
This is the seam where the recorder and IndexedDB get wired together:

     const db = new IndexedDBStorage();
     await db.init();

     const rec = new ScreenRecorder({
       enableWebcam,
       webcamOptions: { webcamPosition, webcamSize, webcamBorderRadius: 12, frameRate: 15 },
       onDataAvailable: async (blob) => { await db.storeChunk(blob); },   // every 5 s
       onStop: async () => {
         setIsProcessing(true);
         const finalBlob = await db.combineChunks();                      // stitch
         await db.clearChunks();
         db.close();
         setIsProcessing(false);
         onRecordingComplete?.(finalBlob);                                // hand to page.tsx
       },
       onError: (err) => { setError(err.message); toast(err.message, 'error'); },
     });
     await rec.start();

Three effects: clear stale chunks on mount (clearAllRecordings), a 1-second timer,
and a 2-second storage-size poll (both active only while recording).
Three mutually-exclusive render states: isProcessing (spinner), isRecording
(timer + "X MB saved" + red stop button), and idle (webcam toggle, WebcamPreview,
blue record button).

WebcamPreview.tsx - POSITION + SIZE PICKER
Purely presentational (controlled by props): a mini screen mockup with 4 corner
buttons (active = blue, scaled up) and a size slider (10-40%). Firing
onPositionChange / onSizeChange bubbles the choice up.

UploadProgress.tsx - THE STATUS PANEL
Renders one of four states from progress.status: uploading (shimmer bar + bytes),
processing (pulsing bar), complete (URL + "View on YouTube" + "Copy Link"), error
(red box). Copy uses navigator.clipboard.writeText, flips to "Copied" for 2 s, and
toasts.

Toaster.tsx - NOTIFICATIONS
A React Context exposes one toast(message, kind) function; useToast() reads it.
Each toast auto-dismisses after 4000 ms and is color-coded (green / red /
neutral). Rendered in a fixed bottom-right stack with aria-live="polite".

TAKEAWAY: RecordingControls owns the recorder<->IndexedDB wiring; the other three
just render what they're given.

================================================================================
13. INTENTIONAL DESIGN DECISIONS
================================================================================

These are deliberate, not bugs:

   Suspense shells            useSearchParams() build-errors in Next 15 without a
                              <Suspense> boundary. Both page.tsx and
                              callback/page.tsx export a shell wrapping the real
                              inner component.
   5-min token buffer         Refresh early so a token never dies mid-upload.
   Video ID from final chunk  Read id from the 200/201 body, not a separate GET
                              (the extra request used to cause a YouTube API error).
   clearAllRecordings on mount Wipe chunks left by a crashed session.
   youtube.upload scope       Avoids the restricted-scope Google audit; only shows
                              an "unverified app" warning.
   Codec fallback             vp9 -> vp8 -> h264 -> webm; download extension stays
                              .webm.
   AudioContext merge         System audio (if opted in) is blended with the mic;
                              otherwise mic only.


================================================================================
14. KNOWN ROUGH EDGES
================================================================================

Non-blocking, but worth knowing:

   1. No OAuth CSRF "state" parameter - the callback can't distinguish a
      legitimate redirect from a forged one. Standard hardening, missing.
   2. resumeUpload() is dead code - implemented but never called, so a mid-upload
      network drop errors out instead of resuming.
   3. Live webcam adjustment is a no-op - recorder state is set AFTER
      await rec.start(), and the update handlers run from the idle screen where
      recorder is still null. Harmless today (the picker isn't shown mid-recording).
   4. Webcam PiP assumes 16:9 - a 4:3 webcam gets stretched.
   5. pause() / resume() are unused - no pause button is rendered.
   6. lint script is unconfigured - adding an ESLint flat config + switching to the
      ESLint CLI would make `npm run lint` run cleanly.

--- THE 30-SECOND PITCH (TECHNICAL) -----------------------------------------

"YouTube Loom is a client-heavy Next.js app that records your screen - plus mic
and an optional webcam picture-in-picture - and uploads it straight to your own

--- THE STAR STORY ----------------------------------------------------------

SITUATION
I regularly needed to record my screen and get it onto YouTube - walkthroughs,
demos, tutorials. Every tool had the same friction: Loom caps free recordings,
plain screen recorders dump a giant file I then upload by hand, and anything that
stored my videos server-side meant paying or trusting someone else with my
content. Browser-based ones would crash the tab on long recordings. I wanted
something that recorded my screen and pushed it straight to MY OWN channel, with
no length limit and nothing stored on a server I don't control.

TASK
Build exactly that, solo: a browser app that captures screen + mic + optional
webcam, handles arbitrarily long recordings without crashing, and uploads
directly to YouTube - while staying essentially free to host and never touching
my video data server-side.

ACTION
I made a deliberate architectural bet: push all the heavy lifting into the
browser so there's no server storage or bandwidth cost. Four things made it work:

  1. RECORDING - combined getDisplayMedia, getUserMedia, and an AudioContext
     mixing bus to merge screen, mic, and system audio into one stream. For
     webcam PiP, I composite the webcam over the screen on a hidden <canvas> at
     15fps and use captureStream() to turn it back into one video track.

  2. THE NO-LIMITS PROBLEM - instead of holding the whole video in RAM, I have
     MediaRecorder emit a 5-second chunk every 5s and stream each one straight to
     IndexedDB (on disk). Memory stays flat whether it's 30 seconds or 3 hours.
     On stop, I reassemble the chunks in timestamp order.

  3. DIRECT UPLOAD - implemented YouTube's resumable upload protocol by hand:
     announce metadata to get a session URL, then send the file in 5MB
     Content-Range PUTs, with exponential-backoff retries on 5xx errors.

  4. SECURITY - OAuth needs a client_secret that can't live in the browser, so I
     added two tiny Next.js API routes as a secret-relay; the browser only ever
     sees the resulting token. I scoped the request to youtube.upload only -
     least privilege, and it sidesteps Google's restricted-scope audit.

  I also wrote a 42-test suite (Vitest) covering the auth logic, the upload state
  machine with mocked fetch, and IndexedDB via fake-indexeddb.

RESULT
It does exactly what I needed: record, edit title/privacy, hit upload, get a
YouTube link - no length ceiling, zero server storage cost, deployed as a static
site plus two stateless functions on Vercel. The hardest-won piece was the
resumable-upload state machine (see the deep-dive below). If I took it further:
httpOnly cookies for tokens, an OAuth CSRF state parameter, and finishing the
resume-on-dropped-connection path I stubbed but didn't complete.

  A note on metrics: this project has no "10k users" or "40% faster" number - its
  wins are CAPABILITY wins (no length ceiling, no storage cost, direct upload).
  Frame results around those, not a fabricated stat. The strongest concrete
  "result" is a true anecdote if you have one - e.g. "I've recorded multi-hour
  sessions and memory never spikes." Use a real story over an invented metric.

Q: Why did you build this?

Q: Was it solo or a team?

Q: What are you most proud of?

--- ARCHITECTURE & DESIGN ---------------------------------------------------

Q: Why no backend for the video itself? What's the trade-off?
A: Cost and simplicity - we never store or egress gigabytes, so hosting is
   basically free and there's no upload-size ceiling. The trade-off: we give up
   everything a server enables - server-side transcoding, a share/analytics
   layer, resumable-across-sessions uploads, and any processing the browser
   can't do. It also ties us to the user having a YouTube account.

Q: Why Next.js if it's mostly client-side?
A: Two reasons: (1) the App Router gives us the two server routes (the secret
   relay) in the same project with zero extra infra; (2) easy Vercel deploy.
   We're not using SSR for the app itself - the home page is a client component.

Q: The pitch is "no memory limits," but combineChunks() does
   new Blob(allChunks). Isn't the whole video in memory at the end?
A: A Blob is a handle, not necessarily bytes in the JS heap - browsers can back
   large Blobs with disk/temp storage, and the chunks came from IndexedDB
   (on disk) in the first place. The upload reads it back with blob.slice(),
   which is a lazy range reference, not a copy. So peak JS heap stays small; the
   OS/browser manages the backing store. The honest caveat: it relies on the
   browser's Blob implementation, not an explicit stream.

Q: Why 5-second chunks specifically? Why not 1s or 60s?
A: It's a balance. Smaller chunks = more IndexedDB writes and overhead; larger
   chunks = more data lost if the tab crashes between writes and a longer flush
   on stop. 5s is a reasonable middle. It's a tunable constant
   (mediaRecorder.start(5000)), not a hard requirement.


--- SECURITY (the section interviewers push hardest on) ---------------------

Q: You put client_secret in the app. How is that safe on a public web app?
A: The secret is only ever read server-side in the two API routes (env var with
   NO NEXT_PUBLIC_ prefix, so Next never bundles it into client JS). The browser
   only ever sees the resulting tokens. The NEXT_PUBLIC_ naming convention IS the
   boundary. What the browser CAN see is the client_id and redirect_uri, which
   are public by design in OAuth.

Q: Tokens are in localStorage. What's the risk, and what would you change?
A: localStorage is readable by any JavaScript on the page, so an XSS bug leaks
   the access + refresh tokens. The stronger pattern is httpOnly, Secure,
   SameSite cookies set by the server, so JS can never read them - but that
   requires routing all YouTube calls through our server (losing the
   direct-to-YouTube benefit) or a session layer. For this app's threat model
   (no other user data, tokens scoped to youtube.upload only) it's an accepted
   trade-off, but I'd flag it in a real product.

Q: You mention there's no CSRF state parameter. Why does that matter?
A: Without a random state value that we generate before redirect and verify on
   callback, an attacker could feed the victim a crafted /auth/callback?code=...
   and potentially bind the victim's session to the attacker's account (login
   CSRF). The fix is one-line-ish: generate a random state, stash it
   (sessionStorage), include it in startOAuthFlow(), and reject the callback if
   it doesn't match.

Q: Is the youtube.upload scope choice a security decision?
A: Partly. It's least-privilege - the app literally only needs to upload, so it
   asks for nothing more (can't read, delete, or manage the channel). The bonus
   is practical: the broad "youtube" scope is a "restricted" scope needing a paid
   Google security audit; youtube.upload is only "sensitive," so publishing shows
   an "unverified app" warning instead of a hard block.


--- CONCURRENCY & CORRECTNESS -----------------------------------------------

Q: ondataavailable fires async storeChunk() calls. On stop, combineChunks()
   reads everything. How do you know you don't miss the last chunk or get them
   out of order?
A: Two safeguards. Ordering: every chunk is written with a timestamp, and
   getAllChunks() sorts by it before combining - so even if IndexedDB writes
   resolve out of order, the assembled order is correct. The last chunk: calling
   MediaRecorder.stop() causes it to flush a final ondataavailable BEFORE onstop
   fires, and our onStop handler awaits combineChunks(), so the final write is in
   flight. This is the one genuinely race-prone spot: if that last storeChunk()
   hasn't resolved when combineChunks() reads, the tail could be missed. A
   hardened version would await the outstanding write explicitly.

Q: React StrictMode is on. What does that do to your effects?
A: In development, StrictMode intentionally double-invokes effects to surface
   impurities. So the mount effect that calls clearAllRecordings() runs twice in
   dev - harmless here because clearing an already-clear store is idempotent. In
   production it runs once. It's a good example of why that cleanup was written
   to be safe to repeat.

Q: What happens if the access token expires DURING a long upload?
A: It can fail mid-upload - we fetch a valid token once at the start via
   getValidAccessToken() (which refreshes if it's within the 5-min buffer), but
   we don't re-check between chunks. The 5-min buffer covers most cases; a truly
   long upload past the token lifetime would 401. The resumable protocol + the
   (currently unused) resumeUpload() are exactly what you'd wire up to recover.


--- ERROR HANDLING & EDGE CASES ---------------------------------------------

Q: What happens if the user denies screen-share permission?
A: getDisplayMedia() rejects; start() catches it, runs cleanup() to release any
   partial streams, calls onError, and re-throws. RecordingControls shows the
   error and toasts it. No half-open camera/mic is left running.

Q: Only 5xx triggers a retry. What about a 401 or 403 mid-upload?
A: Those are NOT retried - they're auth/permission failures where retrying is
   pointless, so uploadChunk throws immediately and the UI shows an error.
   Retries are reserved for transient server errors (5xx) with exponential
   backoff. That's deliberate: retrying a 4xx just wastes time.

Q: The download filename is `${videoTitle}.webm` but the codec might be H.264.
   Problem?
A: The container is always WebM here (all codec choices are inside video/webm),
   so .webm is correct. If we added an mp4 container we'd need to derive the
   extension from the chosen mimeType instead of hardcoding it.


--- TESTING -----------------------------------------------------------------

Q: You have 42 tests but nothing tests recording. Why, and is that OK?
A: MediaRecorder, getDisplayMedia, Canvas.captureStream, and requestAnimationFrame
   don't exist in jsdom, so unit-testing recorder.ts/compositor.ts there would
   mean mocking the entire browser - you'd be testing mocks, not behavior. The
   right tool is an E2E test in a real browser (Playwright with fake device
   flags), which isn't set up. So we test what's meaningfully unit-testable (auth
   logic, upload state machine with mocked fetch, IndexedDB via fake-indexeddb,
   component rendering) and accept that the media pipeline needs manual/E2E
   verification.

Q: How did you test the uploader without hitting YouTube?
A: Stubbed global fetch (vi.stubGlobal) to return canned responses - a Location
   header for initiate, a 200 with an id for the chunk - then asserted the
   returned videoId and that progress reached 100. Also tested the failure paths
   (initiate not ok, missing Location).


--- SCALABILITY & "WHAT WOULD YOU DO DIFFERENTLY" ----------------------------

Q: If this got popular, what breaks first / what would you change?
A: The app itself scales trivially - it's static + two stateless routes on
   Vercel; the heavy lifting is on each user's machine and Google's servers.
   The real limits are external: YouTube Data API v3 has a daily quota (uploads
   cost ~1600 units against a default 10,000/day pool), so at scale we'd need
   quota increases or per-user OAuth apps. Product-wise the "unverified app"
   warning caps adoption until we pass Google verification.

Q: Top 3 things you'd improve given a week?
A: (1) Security: move tokens to httpOnly cookies and add the OAuth state param.
   (2) Reliability: wire up resumeUpload() so a dropped connection resumes
   instead of failing. (3) UX/correctness: fix the 16:9 webcam-stretch (read the
   real aspect ratio), await the final chunk write before combining, and add a
   Playwright E2E test for the record->upload happy path.

Q: What was the hardest part to get right?
A: The resumable upload state machine - specifically that the video id comes from
   the final chunk's 200/201 body, not a separate query. An earlier version sent
   an extra empty PUT to fetch the id and that returned a YouTube API error;
   capturing id inline from the last chunk fixed it. Getting the Content-Range
   math and the 308-vs-200 handling exact was the fiddly part.
